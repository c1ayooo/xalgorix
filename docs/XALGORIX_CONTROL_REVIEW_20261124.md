# Xalgorix 设计与实现审查 · 2026-11-24

当前快照已经实现了信息图读取、worker 停滞上报、planner 干预和引擎超时回收。最影响运行可信度的偏差出在三个环节。满池会延迟 planner 处理已有 worker，进展计时未能辨别实质增量，终止路径也不能始终证明是谁停了哪个 worker、它是否真的退出。第五轮复盘支持调查这些问题，但不足以把每次取消或全部零分时间归给同一个原因。

## 哪些约束过严

**容量限制的适用范围过宽。** 限制新增任务有清晰的资源理由。读取现有状态、处理停止请求也受同一个空槽条件约束，会在所有 worker 都忙时削弱监督。普通执行预算的 30 分钟下限只影响合同时间的计算，仍有独立停滞回收、操作者取消和正常返回等出口。把它理解成“每个 worker 必须跑够 30 分钟”会误诊。代码还对控制面以外、有显式短合同的分析任务应用这一下限，在全局预算允许时，分析合同可能比声明时间更长。见 `internal/orchestrator/pool.go:867`。

**自动回收在不同职责上的覆盖不对称。** 三类 worker 都可上报停滞，但独立进展看门狗只覆盖执行 worker。控制面和分析任务仍受自身预算约束，也可经 planner 或人工结束。观察告警、独立回收、任务预算是三种不同保证。复盘中的重复对账尤其不能用“执行 worker 有 20 分钟回收”解释为已经解决。见 `internal/orchestrator/pool.go:379`、`internal/orchestrator/reclaim.go:87`。

**目标授权、人工确认、证据来源和 finding 验证应维持独立判断。** 本轮材料没有逐次合法操作被这些门错误拒绝的样本。外部平台接受答案，可以支持“完成了这个平台任务”，却不能单独支持一份可复核的漏洞报告。用比赛得分反推报告门过严，会掩盖目标结果、工作回执、已验证发现三者的差别。现有 worker 完成回执本身标注 inferred，只存状态和摘要长度等元数据，也不宜计为一条新的实测证据。见 `docs/INFO_AS_GRAPH_SPEC.md:40`、`internal/orchestrator/pool.go:972`、第五轮复盘 §4.5。

## 验证与验收

离线运行了原仓进展存储的 4 个 Go 测试，覆盖空记录、时间更新、并发与近期进展窗口，全部通过。另取快照中原样的等待、唤醒和回收函数，用内存替身做了 2 个隔离检查。已挂起的 stall 信号未解除满池等待，释放槽位后等待正常结束。对 typed 停滞取消返回拒绝后，替身记录到第二次普通取消。这两项是函数级验证，未模拟真实模型、数据库或网络执行。

完整 orchestrator 包测试未进入测试阶段。离线环境缺少模块依赖，归档本身还缺少 `internal/honeydetect/honeydetect.go:23` 要求嵌入的 `signatures.json`。已有专项测试分别覆盖容量等待、两轮无纠偏后的提醒、正常回收；这些单项行为不足以证明它们组合之后可靠。设计版本也要区分：`PLANNER_OBSERVATION_AND_CORRECTION.md` 自标草案，它描述的长工具保护和观察窗适合作为验收目标；第五轮报告 §11 则记录了另一项引擎确定性回收设计。两者对数字和决策者有差异，不能把任一组数字当作统一生效合同。

平台验收可以完全使用假 worker 和本地状态库。一次运行分别观察“停滞首次可见 → planner 记录决定”“决定停止 → 执行确认退出”“退出 → 图终态及原因提交”。把重复写同值、长期等待后正常返回、宽限期恢复、拒绝取消、数据库写原因失败和换租后旧 worker 返回作为独立样本。每个样本核对 run、unit、派发 agent、决定来源和终态；补充记录无实质增量时间、误停数、终态后仍活动数、原因缺失数。这样可以验证监督和审计是否可靠，也能在后续 benchmark 中定位时间花在哪里。
